## Thèmes

`src/lib/theme.svelte.ts`. **Un thème sombre, Nuit, et un clair, Papier** (décision de l'utilisateur, 2026-11-14 : les 6 autres, Charbon, Crépuscule, Braise, Sable, Menthe, Lavande, ont été retirés pour n'avoir qu'une palette à soigner par mode). Le joueur ne choisit que le mode (`appearance` : `system` = selon Windows, par défaut / `dark` / `light`) dans la section « Apparence » des Réglages. Les réglages `theme_dark` / `theme_light` restent lus et écrits : un ancien thème retiré retombe sur Nuit ou Papier (`byId`). Un thème = les variables `--color-*` de `app.css` posées sur `<html>` (`applyTheme`, `$effect` de chaque fenêtre, `theme-changed` pour la fenêtre compacte) + `color-scheme` + barre de titre Windows (`setTheme`, permission `core:window:allow-set-theme`). **Piège** : le thème imposé à la fenêtre change aussi ce que le moteur web répond à `prefers-color-scheme` ; en mode « selon Windows », la fenêtre est rendue au système (`setTheme(null)`), jamais forcée, sinon le vrai réglage de Windows n'est plus visible. Dernier thème gardé dans `localStorage` et posé par `main.ts` avant le premier affichage (pas d'éclair sombre). **Toute couleur de l'interface passe par ces variables** ; texte sur un bouton d'accent : `text-on-accent`, `text-white` seulement sur `bg-danger`. Les couleurs des étiquettes ne suivent pas le thème. Revue dans l'interface simulée : couper les animations (`motion.pref = "off"`), sinon les transitions de couleur restent figées dans le panneau masqué et faussent les captures.

## Export / import de guides

`src-tauri/src/guides.rs`. Un fichier `.json` unique (format `grimoire-guide`, `version` 1 ; l'ancien `chasse-succes-guide` reste accepté), images des blocs incluses en base64. Contient les cartes (succès repéré par `api_name`, sinon nom ; cartes libres par titre), leur place dans l'espace, les étiquettes (nom + couleur) et les blocs ; **jamais** la progression Steam, les coches, le compte, le temps de jeu ni les réglages. Case « Garder l'état des compteurs, listes et chronos » (sauvegarde) décochée par défaut : guide vierge (compteurs à 0, listes décochées, chronos sans temps ni record, cartes « à faire », pas d'épingle). Import = fusion : jeu ajouté depuis Steam s'il manque, blocs ajoutés après les existants, ce qui existe à l'identique n'est pas recréé (réimporter ne double rien ; une image se compare par sa légende), disposition du Tableau reprise seulement si l'espace est vide, succès introuvable → carte libre « Succès introuvable : … ». **Import tout ou rien** : tout se fait dans un savepoint SQLite (`SAVEPOINT guide_import`) ; en cas d'erreur la base revient à l'état d'avant et les images recopiées sont effacées. Pour que ce soit possible, les fonctions de `db.rs` ouvrent des `savepoint()` (imbricables) et non des `transaction()` (un `BEGIN` échoue dans une transaction déjà ouverte) : garder cette règle. Volontairement hors du « tout ou rien » : le jeu ajouté depuis Steam juste avant (commande `guide_import`) reste ajouté si l'import échoue ensuite (jeu valide, évite de le retélécharger au nouvel essai). Étiquettes du guide : noms débarrassés des espaces autour avant la recherche ; une étiquette refusée (vide, plus de 40 caractères) est ignorée et signalée dans le bilan (`ignored_tags`), sans bloquer l'import. Fenêtres Enregistrer / Ouvrir de Windows ouvertes **côté Rust** (`tauri-plugin-dialog`, aucune permission JS). Interface : menu « ⋯ » du jeu (Exporter / Importer), `ExportDialog.svelte`, bouton « Exporter le guide d'abord… » à la suppression d'un jeu, lien « Importer un guide… » dans « Ajouter un jeu ». Après un import, la vue du jeu est recréée (`viewVersion` dans `App.svelte`).

## Progression Steam des succès

(demande de l'utilisateur, 2026-11-13) Barre « 37 / 50 » affichée automatiquement, sans réglage, sur chaque succès non obtenu que Steam suit (liste, carte, mode compact ; masquée sous l'anti-spoiler). Lue dans le cache local (`steam/local_cache.rs`) : bit du succès → `progress { min_val, max_val, value { operation "statvalue", operand1 <stat> } }`, stat décrite dans `stats` (INT ou FLOAT), valeur = `data` de la même clé dans le fichier du compte (bits d'un f32 si FLOAT ; défaut du schéma si absente). Constat sur le PC de l'utilisateur : 284 jeux sur 984, seule l'opération `statvalue` existe. Colonnes `achievements.progress_value/min/max` (migration v9), dernière valeur gardée quand la source n'en donne pas (`COALESCE`). `watch.rs` enregistre aussi un changement de progression seul (événement `steam-progress` sans succès débloqué, la liste se recharge par `refreshed_at`). La fréquence dépend du jeu (certains n'écrivent leurs stats qu'en fin de niveau). Composant `SteamProgress.svelte`. Sonde : `cargo run --example probe -- <appid>` liste les succès suivis.

## Actualisation automatique

Constat de l'utilisateur (Cookie Clicker, 2026-11-13) : Steam réécrit `UserGameStats_<compte>_<appid>.bin` dès le déblocage, jeu ouvert. `src-tauri/src/watch.rs` : fil de fond lancé au démarrage, toutes les 2 s regarde la date de modification de ce fichier pour chaque jeu de la bibliothèque (lecture seule ; compte Steam du PC relu toutes les 60 s, même déjà trouvé : en cas de changement de compte dans Steam, les dates vues sont oubliées et les fichiers du nouveau compte servent de nouvelle référence, sans actualisation ; Steam introuvable un moment : compte d'avant gardé). Fichier changé → relecture du **seul cache local** (pas de réseau, la rareté en base est gardée par `save_game`) ; rien n'est écrit si l'état des succès dans le fichier n'a pas changé (statistiques seules). **Date de modification retenue seulement après une lecture réussie** (état des succès connu) : un fichier verrouillé ou à moitié écrit par Steam au moment du passage est relu au passage suivant, sinon le succès débloqué était manqué jusqu'à la modification suivante. Si l'état en base change (coches manuelles respectées) : événement Tauri `steam-progress` `{ game, unlocked }` vers les deux fenêtres. Fenêtre principale : `upsert` (liste, bannière, célébration du 100 %) et notification « 🏆 Succès débloqué » (`showToast(…, { untilSeen: true })` : reste affichée tant que la fenêtre n'est pas au premier plan, puis 10 s) ; fenêtre compacte : coche et message (10 s). Un seul carillon : la fenêtre compacte si elle est ouverte (`shortcuts.live`), sinon la principale.

Refonte (2026-11-13) :

Haut / Bas changent la sélection (boucle, cadre bleu, clic = sélection), Gauche / Droite agissent : compteur −1 / +1 ; chrono remis à zéro **à l'arrêt seulement** / lancé-arrêté ; vidéo −10 s / lancée, lecture-pause ; liste : décoche le dernier coché / coche le suivant. ## Sections de l'espace de travail

(demande de l'utilisateur, 2026-11-13, à la place d'une vue « Feuille de route » séparée) Groupes de cartes nommés, pleine largeur, repliables, facultatifs. Une carte sans section est dans la **zone du haut** : un jeu sans section s'affiche comme avant.

- Base : table `sections` (migration v10 : `id`, `appid`, `title`, `position`, `collapsed`) et colonne `workspace_items.section_id` (`ON DELETE SET NULL`). `save_workspace` n'accepte qu'une section du même jeu (sinon hors section). Commandes `sections_list`, `section_create` (à la fin), `sections_save` (titre, repli, ordre ; ne crée ni ne supprime rien), `section_delete`. `grid` d'une carte est **relatif à sa section**.
- `Workspace.svelte` : un tableau gridstack (ou une pile svelte-dnd-action en vue Liste) **par zone** ; `items` toujours rangé zone du haut puis sections dans l'ordre (mode compact, ordre personnel). En-tête : poignée ⠿, repli, titre modifiable, bilan « ✓ obtenus / succès » et cartes libres, menu (Monter, Descendre, Supprimer). Boutons « + Section », « replier / déplier les sections ».
- **Glisser une carte d'un tableau à l'autre** : gridstack (`acceptWidgets`) déplace l'élément dans le DOM de l'autre grille, alors que Svelte en est propriétaire. Dans `dropped` (Board.svelte), l'élément est retiré de la grille d'arrivée, rendu à sa place d'origine (notée à `dragstart` sur `.grid-stack-item`, la cible de l'événement pouvant être la poignée) et caché, puis `onmovein` change sa section : Svelte le supprime et le recrée dans la bonne section. Test dans le volet du navigateur : événements souris progressifs, plus `mouseleave` / `mouseenter` simulés sur les grilles.
- Autres façons de changer une carte de section : menu « ⋯ » de la carte (« Déplacer vers « … » », « Sortir de la section » ; place libre trouvée, taille gardée), et succès glissés depuis le panneau sur un en-tête de section (même repliée).
- Réordonner : glisser natif de la poignée (type `application/x-grimoire-section`), trait d'insertion ; les cartes ignorent la souris pendant ce glisser (iframes YouTube).
- Supprimer une section vide : sans question. Sinon question (demande de l'utilisateur) : « Garder les cartes » (elles passent dans la zone du haut, sous ses cartes) ou « Retirer aussi les cartes » (les succès quittent l'espace en gardant leurs blocs, les cartes libres sont supprimées avec leur contenu).
- **Apparence** (refonte demandée par l'utilisateur, 2026-11-14, après une maquette) : chaque zone est un cadre (`.zone-frame`, coins de 6 px) dans la couleur de sa section (`--zone-color`), bandeau de titre teinté avec pastille de couleur, bilan « obtenus / succès » et barre de progression. Zone « Hors section » encadrée en gris, seulement s'il y a des sections. **Zone d'arrivée éclairée** (`is-target`, pointillés et fond teinté) pendant un glisser : depuis le panneau (événements `dragover`) ou d'un tableau à l'autre (`ondragcard` de Board.svelte, puis position de la souris comparée aux `[data-zone]` : la carte glissée est sous le curseur, les zones ne reçoivent pas l'événement). Aperçu de la place d'arrivée de gridstack dans la couleur de la zone.
- **Couleurs** : 8 noms (`SECTION_COLORS`, mêmes listes en Rust et en TS : violet, bleu, turquoise, vert, ambre, corail, rose, gris), colonne `sections.color` (migration v11). La teinte dépend du thème (`sections` de chaque thème dans theme.svelte.ts, variables `--section-<nom>`), pour rester lisible sur Nuit comme sur Papier. Nouvelle section : première couleur pas encore prise. Choix par la pastille de l'en-tête ou « Changer la couleur… » (nuancier sous l'en-tête). Palette fermée plutôt que couleur libre, pour que les sections aillent ensemble.
- Export / import de guides : `sections` (titre, repli, couleur) dans le fichier, `workspace.section` = rang de la section ; à l'import, une section du même nom est reprise, sinon créée.

## Cartes libres

Blocs sans succès, choisis plutôt que des blocs isolés dans le Tableau.

- Table `free_cards` (migration v8 : `id`, `appid`, `title`). `workspace_items` et `blocks` reconstruites : chaque ligne a soit `achievement_id`, soit `card_id` (contrainte CHECK), les `id` des blocs sont conservés. ## Animations et son

- Module `src/lib/motion.svelte.ts` : réglage `animations` (`system` = selon Windows, par défaut / `on` / `off`), section « Interface » des Réglages, synchronisé avec la fenêtre compacte (`motion-changed`). Animations réduites → attribut `data-reduced-motion` sur `<html>` (coupe tout le CSS, `app.css`) **et** `dur()` qui renvoie 0 pour ce qui est lancé en JS (transitions Svelte, `flip`, svelte-dnd-action, gridstack via `setAnimation`). Toute nouvelle animation JS doit passer par `dur()` / `reduced()`, jamais `matchMedia` directement.
- Durées communes `SPEED` (120 / 180 / 300 ms). Transitions `backdrop` et `pop` (fenêtres modales, menus « ⋯ », étiquettes, notification, menu d'ajout de bloc en entrée seulement car il est dans le flux de la carte). `<dialog>` natif (ajout de jeu) : classe CSS `dialog-pop`.
- `appear` : changement de jeu et accueil. `arrive` : une carte ne s'anime à l'entrée que si son succès vient d'être ajouté (`arrivals`, rempli par `addToWorkspace`), pas au chargement. `leave` : animation de sortie avant le retrait (`data-card` sur la carte), limitée dans le temps pour ne jamais retarder le retrait. `appear`/`arrive` lisent le réglage avec `untrack` (sinon l'attachement se rejoue).
- Son : `src/lib/sound.svelte.ts`, réglage `check_sound` (désactivé par défaut), carillon de deux notes synthétisées à la coche (pas au décochage), fenêtre principale et compacte (`sound-changed`). Le bip des raccourcis y est aussi.

## 100 % et célébration

- `games.completed_at` tenu à jour par `update_completion` (`db.rs`) après chaque import, coche ou reset : posé quand tous les succès non retirés sont obtenus (coche manuelle → maintenant ; actualisation → date du dernier succès Steam), effacé si le jeu n'est plus à 100 %. Migration v7 : colonne `celebrated` et date des jeux déjà terminés.
- Célébration (`Celebration.svelte`) **une seule fois par jeu** : déclenchée dans `App.svelte` (`upsert`) quand un jeu passe à 100 % **ou est ajouté déjà terminé** (ajout ou import de guide ; demande de l'utilisateur, 2026-11-13) et que `celebrated` est faux, puis `game_mark_celebrated`. Un jeu supprimé puis rajouté est donc recélébré. Rejouable depuis le badge « 🏆 100 % » de la bannière. Fin de parcours : « Continuer », et en liens discrets « Exporter le guide… » (`ExportDialog`) et « Retirer le jeu… » (confirmation dans la boîte, avec « Exporter d'abord… »).
- Récap (`game_recap`) : date du 100 %, temps de jeu relu dans `userdata/<compte>/config/localconfig.vdf` (`steam/playtime.rs`, aussi lu à chaque import), succès obtenu le plus rare.
- **Plus de confettis** (jugés « cheap » par l'utilisateur, 2026-11-13) : éclat doré autour de la boîte (`.gold-aura` dans `app.css` : liseré conique qui tourne via `@property --aura-angle`, halo qui respire, reflet unique à l'apparition `.gold-aura-box`). Animations réduites : liseré et halo figés, pas de reflet.
- Version dorée : classe `.gold-frame` (`app.css`) ; un jeu à 100 % reste doré dans le panneau jusqu'à ce que le joueur le retire. Ancien réglage `hide_completed` abandonné (la valeur peut rester en base, sans effet).

## Glisser-déposer

- Vue Tableau : `gridstack` (`src/lib/Board.svelte`), position/taille en base (`workspace_items.grid_*`, migration v4). Svelte rend les cartes, gridstack les positionne : la mise en place d'une carte (`setupItem`) ne doit s'exécuter **qu'une fois** (`untrack`), sinon chaque enregistrement la remet à son ancienne place. Pour tester sans souris réelle : événements souris simulés progressifs sur `document` (un `left_click_drag` instantané ne suffit pas).
- Tableau libre (`float`) : seules les cartes sous une carte retirée remontent (`closeGap`, après `tick()` sinon la carte retirée revient en base), et toutes avec « tout remonter » (remontée verticale maison, pas `grid.compact()` qui déplace les cartes de côté).
- Vue Liste : `svelte-dnd-action` (`dragHandleZone`, `useCursorForDetection: true`).
- Arrivée depuis le panneau : glisser HTML natif, d'où `dragDropEnabled: false` dans `tauri.conf.json`. Dans le Tableau, la case est calculée à la main (`cellAt`) : **ne pas utiliser `grid.getCellFromPixel`**, qui compare les coordonnées écran à `offsetLeft/offsetTop` et décale la carte. Aperçu de la place d'arrivée, toujours la place libre la plus proche (aucune carte n'est poussée) ; les cartes ignorent la souris pendant ce glisser (sinon les iframes YouTube avalent l'événement).

## Sources Steam (constats, le SPEC date d'avant)

- **`?xml=1` des profils ne marche plus** : renvoie une page HTML.
- Les pages `steamcommunity.com/stats/<appid>/achievements/` et `…/profiles/<id>/stats/<appid>/achievements/` sont rendues côté serveur avec un JSON embarqué (`<script id="valve-ssr-data">` → `renderContext.queryData` → requêtes `["achievements", appid, "schema_v2" | "globalpercentages" | "user_achievements"]`). La page publique fournit donc **l'ID technique, les descriptions des succès cachés, la rareté et le DLC de chaque succès** ; le profil y ajoute l'état et la date. Lecture dans `src-tauri/src/steam/web.rs`.
- Ordre des sources (`load_best`) : le cache local du compte du PC passe avant le lien de profil réglé. Voulu : ce lien vise le propre compte du joueur (réponse de l'utilisateur, 2026-11-14), pas le suivi d'un autre compte. Ne pas inverser.
- La langue des pages se choisit par le cookie `Steam_Language=<langue>` (le paramètre `?l=` est ignoré).
- Profil public + jeu non possédé : la progression arrive quand même, tout à « non obtenu ». Ne pas confondre avec « possédé, rien obtenu ».
- Cache local : bit débloqué = `(stat, bit)` du schéma ↔ champ de bits `data` de la progression ; dates dans `AchievementTimes`.
- Le `gamename` du schéma local est choisi par le développeur et peut être un nom de code (Yakuza 3 Remastered → « RINO », constat de l'utilisateur 2026-11-13) : `library_import` prend d'abord le nom du magasin (`store::app_name`), celui de la source seulement hors ligne. Les noms locaux (liste « jeux lancés sur ce PC », recherche) viennent d'abord des manifestes d'installation `steamapps/appmanifest_<appid>.acf` de chaque bibliothèque (`steam/manifests.rs`, nom officiel), sinon du schéma.
- Recherche « Ajouter un jeu » : un jeu **retiré du magasin** n'est plus dans la recherche du magasin (constat de l'utilisateur, Atelier Ryza: Ever Darkness & the Secret Hideout, 2026-11-13) ; on le trouve parmi les jeux de ce PC (cache + jeux installés jamais lancés), comparaison sans ponctuation, dans les deux sens (`name_matches` dans `library.rs`). Son AppID ou son lien Steam marche aussi (`appdetails` répond encore).
- Le `gamename` du schéma est tantôt au début du fichier, tantôt à la fin (Atelier, Yakuza…) : lire le début, puis la fin, puis tout le fichier (`read_game_name`). Avant cette correction, une partie des jeux du cache n'avait pas de nom local (introuvables par nom).
