## Règles impératives

- Ne jamais écrire dans les fichiers de Steam : lecture seule.
- Ne jamais exécuter de commande console Steam : seulement les afficher.
- Tester chaque étape sous Windows 11 avant de continuer. **Décision de l'utilisateur (2026-11-12)** : Windows seulement, Linux non pris en charge (l'utilisateur ne peut pas le tester). Le code reste portable (chemins Steam Linux conservés, pas de code propre à Windows sans nécessité), mais aucune version Linux n'est publiée ni annoncée.
- Garder la logique Steam isolée dans un module Rust dédié, réparable seul si Valve change un format.
- Licence GPL-3.0 : toute dépendance ajoutée doit être compatible.

## Stack

Tauri 2 (cœur Rust dans `src-tauri/`) + Svelte 5 + TypeScript + Vite + Tailwind 4 (interface dans `src/`).

- **Base de données** : SQLite via `rusqlite`, uniquement côté Rust (`src-tauri/src/db.rs`). L'interface ne touche jamais la base : elle appelle des commandes Tauri (`src-tauri/src/library.rs`). Migrations par `PRAGMA user_version` : ne jamais modifier une migration existante, en ajouter une.
- **Données** : `%APPDATA%\Grimoire` (`~/.local/share/Grimoire`), **pas** le dossier de l'identifiant qui contient le pseudo de l'utilisateur (décision de l'utilisateur, 2026-11-13) : `src-tauri/src/data_dir.rs`, qui déplace au premier lancement les données de l'ancien dossier `%APPDATA%\io.github.johnounet.grimoire` et ne réutilise pas un dossier `Grimoire` d'un autre logiciel (repli : `Grimoire (succès)`). Contenu : `donnees.sqlite`, `images/` (jaquettes et images des blocs, servies par le protocole asset : portée donnée à l'exécution, `asset_protocol_scope().allow_directory`, celle de `tauri.conf.json` est vide), `backups/`. L'identifiant reste utilisé par le dossier interne de la WebView (`%LOCALAPPDATA%`) et l'installeur.
- Les guides (étapes suivantes) devront référencer `achievements.id`, stable lors des actualisations.

**Page d'accueil, choix faits** : `src/lib/Home.svelte`. Bibliothèque vide (premier lancement) : bienvenue en 3 étapes (ajouter un jeu, préparer son guide, mode compact), bouton « Ajouter mon premier jeu » et lien « importer un guide » ; la fenêtre d'ajout ne s'ouvre plus d'elle-même. Sinon, tableau de bord ouvert par le bouton « Accueil » du panneau (au-dessus de la vitrine), **jamais imposé au démarrage** : bilan (succès obtenus, progression, jeux à 100 % / en cours, temps de jeu), 4 jeux les plus proches du 100 % (moins de succès restants), 8 derniers succès débloqués tous jeux confondus (`home_recent_unlocks`, succès datés seulement). Une coche manuelle est désormais datée du jour (`set_unlocked` : `COALESCE(unlock_time, now)`, la date de Steam est gardée) ; les anciennes coches restent sans date (« coché à la main »). `App.svelte` : `page` = `game` / `home` / `showcase`. Au démarrage, le dernier jeu consulté (réglage `last_game`) est rouvert, sinon le premier du panneau. Interface simulée : http://localhost:1420/?empty pour une bibliothèque vide.

**Thèmes, choix faits** : `src/lib/theme.svelte.ts`. 4 sombres (Nuit, Charbon, Crépuscule, Braise) et 4 clairs (Papier, Sable, Menthe, Lavande), chacun avec son fond **et** son accent. Le joueur choisit un thème par famille (réglages `theme_dark`, `theme_light`) et le mode (`appearance` : `system` = selon Windows, par défaut / `dark` / `light`) dans la section « Apparence » des Réglages (aperçus dessinés avec les couleurs du thème, `paletteStyle`). Un thème = les variables `--color-*` de `app.css` posées sur `<html>` (`applyTheme`, `$effect` de chaque fenêtre, `theme-changed` pour la fenêtre compacte) + `color-scheme` + barre de titre Windows (`setTheme`, permission `core:window:allow-set-theme`). **Piège** : le thème imposé à la fenêtre change aussi ce que le moteur web répond à `prefers-color-scheme` ; en mode « selon Windows », la fenêtre est rendue au système (`setTheme(null)`), jamais forcée, sinon le vrai réglage de Windows n'est plus visible. Dernier thème gardé dans `localStorage` et posé par `main.ts` avant le premier affichage (pas d'éclair sombre). **Toute couleur de l'interface passe par ces variables** ; texte sur un bouton d'accent : `text-on-accent` (foncé sur turquoise et orange), `text-white` seulement sur `bg-danger`. Les couleurs des étiquettes ne suivent pas le thème. Revue dans l'interface simulée : couper les animations (`motion.pref = "off"`), sinon les transitions de couleur restent figées dans le panneau masqué et faussent les captures.

**Export / import de guides, choix faits** : `src-tauri/src/guides.rs`. Un fichier `.json` unique (format `grimoire-guide`, `version` 1 ; l'ancien `chasse-succes-guide` reste accepté), images des blocs incluses en base64. Contient les cartes (succès repéré par `api_name`, sinon nom ; cartes libres par titre), leur place dans l'espace, les étiquettes (nom + couleur) et les blocs ; **jamais** la progression Steam, les coches, le compte, le temps de jeu ni les réglages. Case « Garder l'état des compteurs, listes et chronos » (sauvegarde) décochée par défaut : guide vierge (compteurs à 0, listes décochées, chronos sans temps ni record, cartes « à faire », pas d'épingle). Import = fusion : jeu ajouté depuis Steam s'il manque, blocs ajoutés après les existants, ce qui existe à l'identique n'est pas recréé (réimporter ne double rien ; une image se compare par sa légende), disposition du Tableau reprise seulement si l'espace est vide, succès introuvable → carte libre « Succès introuvable : … ». Fenêtres Enregistrer / Ouvrir de Windows ouvertes **côté Rust** (`tauri-plugin-dialog`, aucune permission JS). Interface : menu « ⋯ » du jeu (Exporter / Importer), `ExportDialog.svelte`, bouton « Exporter le guide d'abord… » à la suppression d'un jeu, lien « Importer un guide… » dans « Ajouter un jeu ». Après un import, la vue du jeu est recréée (`viewVersion` dans `App.svelte`).

**Sauvegardes, choix faits** (V2 du SPEC, demande de l'utilisateur 2026-11-13) : `src-tauri/src/backup.rs`. Dossier `backups/<horodatage>-<sorte>/` dans le dossier des données (nom neutre choisi par l'utilisateur ; l'ancien `sauvegardes/` est renommé au démarrage ; le nom du dossier est affiché dans chaque ligne des Réglages) : `donnees.sqlite` (API de sauvegarde SQLite, feature `backup` de rusqlite), images utilisées par cette base (`images/blocks/` en **liens physiques**, jamais réécrites ; `images/covers/` copiées), `info.json` (date, sorte, nombre de jeux, taille). Dossier écrit sous un nom temporaire puis renommé (une sauvegarde listée est entière). Sortes : `auto` (au démarrage puis toutes les heures si la dernière a 24 h ou plus, pas tant que la bibliothèque est vide ; 7 gardées), `manuel`, `avant-restauration` (jamais supprimées d'office). Restauration : sauvegarde de l'état actuel, `Connection::restore` dans la connexion ouverte, migrations rejouées, images manquantes remises ; refusée pour une base plus récente que le logiciel. Interface : `BackupsSection.svelte` en bas des Réglages ; avant de sauvegarder ou restaurer, `flushBlocks()` ; après restauration, événement `data-restored` (la fenêtre compacte se recharge) et rechargement de la fenêtre principale. `AppState.data_dir` ajouté.

**Progression Steam des succès (demande de l'utilisateur, 2026-11-13), choix faits** : barre « 37 / 50 » affichée automatiquement, sans réglage, sur chaque succès non obtenu que Steam suit (liste, carte, mode compact ; masquée sous l'anti-spoiler). Lue dans le cache local (`steam/local_cache.rs`) : bit du succès → `progress { min_val, max_val, value { operation "statvalue", operand1 <stat> } }`, stat décrite dans `stats` (INT ou FLOAT), valeur = `data` de la même clé dans le fichier du compte (bits d'un f32 si FLOAT ; défaut du schéma si absente). Constat sur le PC de l'utilisateur : 284 jeux sur 984, seule l'opération `statvalue` existe. Colonnes `achievements.progress_value/min/max` (migration v9), dernière valeur gardée quand la source n'en donne pas (`COALESCE`). `watch.rs` enregistre aussi un changement de progression seul (événement `steam-progress` sans succès débloqué, la liste se recharge par `refreshed_at`). La fréquence dépend du jeu (certains n'écrivent leurs stats qu'en fin de niveau). Composant `SteamProgress.svelte`. Sonde : `cargo run --example probe -- <appid>` liste les succès suivis.

**Actualisation automatique, choix faits** : constat de l'utilisateur (Cookie Clicker, 2026-11-13) : Steam réécrit `UserGameStats_<compte>_<appid>.bin` dès le déblocage, jeu ouvert. `src-tauri/src/watch.rs` : fil de fond lancé au démarrage, toutes les 2 s regarde la date de modification de ce fichier pour chaque jeu de la bibliothèque (lecture seule ; Steam recherché toutes les 60 s s'il est introuvable). Fichier changé → relecture du **seul cache local** (pas de réseau, la rareté en base est gardée par `save_game`) ; rien n'est écrit si l'état des succès dans le fichier n'a pas changé (statistiques seules). Si l'état en base change (coches manuelles respectées) : événement Tauri `steam-progress` `{ game, unlocked }` vers les deux fenêtres. Fenêtre principale : `upsert` (liste, bannière, célébration du 100 %) et notification « 🏆 Succès débloqué » (`showToast(…, { untilSeen: true })` : reste affichée tant que la fenêtre n'est pas au premier plan, puis 10 s) ; fenêtre compacte : coche et message (10 s). Un seul carillon : la fenêtre compacte si elle est ouverte (`shortcuts.live`), sinon la principale.

## Sources Steam : constats de l'étape 2 (le SPEC date d'avant)

- **`?xml=1` des profils ne marche plus** : renvoie une page HTML.
- Les pages `steamcommunity.com/stats/<appid>/achievements/` et `…/profiles/<id>/stats/<appid>/achievements/` sont rendues côté serveur avec un JSON embarqué (`<script id="valve-ssr-data">` → `renderContext.queryData` → requêtes `["achievements", appid, "schema_v2" | "globalpercentages" | "user_achievements"]`). La page publique fournit donc **l'ID technique, les descriptions des succès cachés, la rareté et le DLC de chaque succès** ; le profil y ajoute l'état et la date. Lecture dans `src-tauri/src/steam/web.rs`.
- La langue des pages se choisit par le cookie `Steam_Language=<langue>` (le paramètre `?l=` est ignoré).
- Profil public + jeu non possédé : la progression arrive quand même, tout à « non obtenu ». Ne pas confondre avec « possédé, rien obtenu ».
- Cache local : bit débloqué = `(stat, bit)` du schéma ↔ champ de bits `data` de la progression ; dates dans `AchievementTimes`.
- Le `gamename` du schéma local est choisi par le développeur et peut être un nom de code (Yakuza 3 Remastered → « RINO », constat de l'utilisateur 2026-11-13) : `library_import` prend d'abord le nom du magasin (`store::app_name`), celui de la source seulement hors ligne. Les noms locaux (liste « jeux lancés sur ce PC », recherche) viennent d'abord des manifestes d'installation `steamapps/appmanifest_<appid>.acf` de chaque bibliothèque (`steam/manifests.rs`, nom officiel), sinon du schéma.
- Recherche « Ajouter un jeu » : un jeu **retiré du magasin** n'est plus dans la recherche du magasin (constat de l'utilisateur, Atelier Ryza: Ever Darkness & the Secret Hideout, 2026-11-13) ; on le trouve parmi les jeux de ce PC (cache + jeux installés jamais lancés), comparaison sans ponctuation, dans les deux sens (`name_matches` dans `library.rs`). Son AppID ou son lien Steam marche aussi (`appdetails` répond encore).
- Le `gamename` du schéma est tantôt au début du fichier, tantôt à la fin (Atelier, Yakuza…) : lire le début, puis la fin, puis tout le fichier (`read_game_name`). Avant cette correction, une partie des jeux du cache n'avait pas de nom local (introuvables par nom).
